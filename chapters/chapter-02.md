# Chapter 02. IP·DNS·HTTP와 네트워크 기초

[← 이전 장](chapter-01.md) · [전체 목차](../README.md) · [다음 장 →](chapter-03.md)

공식 가이드 연결: **기초** · 권장 2~3시간(통합 실습은 4~6시간)

## 1. 개념

### 브라우저 요청의 이동
브라우저는 DNS에서 도메인의 IP를 찾고, 네트워크 경로로 목적지에 도달한 뒤 TCP/TLS 연결을 맺어 HTTP 요청을 보낸다. DNS 오류, 경로 오류, 방화벽 차단, 인증 실패, 앱 오류는 서로 다른 계층의 문제다. HTTP 403은 보통 요청을 받은 서비스가 접근을 거부했다는 뜻이며, IP 통신 자체가 끊겼다는 뜻과 다르다.

### 주소 범위와 통신 방향
IPv4 CIDR의 `/24`는 앞 24비트가 네트워크 부분이라는 뜻이다. `/24`에는 총 256개 주소가 있고 실제 할당 가능한 수는 플랫폼 예약 정책에 따라 줄어든다. `/23`은 `/24`보다 큰 범위다. 사설 주소는 인터넷에서 직접 라우팅되지 않는다.

Ingress는 자원으로 들어오는 연결, egress는 자원에서 나가는 연결이다. 경로가 있어도 방화벽이 거부하면 통신할 수 없다. NAT는 주소 변환이고 DNS는 이름 해석이다. NAT를 만들었다고 도메인 레코드가 생기지 않는다.

1. /24와 /23 중 더 큰 주소 범위는?

2. DNS와 NAT의 역할은?

3. HTTP 403과 연결 시간 초과를 같은 방법으로 진단하면 안 되는 이유는?

## 3. 실습과 관찰

Cloud Shell에서 `curl -I https://cloud.google.com`을 실행해 상태 코드와 응답 헤더를 관찰한다. `getent hosts cloud.google.com`으로 이름 해석 결과를 확인한다. `10.0.0.0/24`와 `10.0.1.0/24`가 겹치는지 종이에 계산한다. 유료 리소스 생성과 삭제는 없다.

## 4. 실전 시험형 예제

학습용 자체 제작 문제다. 실제 출제 문항이나 시험 덤프가 아니다.

### 문제 1 — 단일 선택

도메인으로는 접속되지 않지만 올바른 IP로 직접 접근하면 연결된다. 우선 확인할 것은?

A. 디스크 스냅샷 정책
B. CPU 개수
C. 결제 통화
D. DNS 레코드와 이름 해석

### 문제 2 — 단일 선택

사설 VM이 외부 패키지 저장소에 접속해야 한다. 외부에서 VM으로 새 연결은 허용하지 않으려 한다.

A. 버킷을 공개한다
B. 공개 DNS에 VM 이름만 등록한다
C. 아웃바운드용 Public NAT를 검토한다
D. 모든 ingress를 허용한다

### 문제 3 — 단일 선택

서버가 403을 반환한다. 가장 직접적인 다음 점검은?

A. 랜 케이블 구매
B. 요청 주체의 인증과 권한
C. CPU 모델 교체
D. 모든 리전 재배치

<details>
<summary>개념 확인 정답과 시험형 문제 해설</summary>

### 개념 확인

1. /23이다.

2. 각각 이름 해석과 주소 변환이다.

3. 도달한 계층과 실패 원인이 다르기 때문이다.

### 시험형 예제

**1. D** — IP 경로가 동작하므로 이름 해석부터 확인한다. 디스크·CPU·통화는 도메인만 실패하는 증거를 설명하지 않는다.

**2. C** — NAT는 외부 IP 없는 VM의 발신 통신에 쓰인다. DNS는 경로를 만들지 않고 ingress 전체 허용과 버킷 공개는 불필요하다.

**3. B** — 응답을 받았으므로 접근 정책과 요청 주체를 본다. 물리 장비·리전·CPU 변경은 근거가 없다.

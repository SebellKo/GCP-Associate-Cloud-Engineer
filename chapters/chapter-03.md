## 1. 개념

### 관리 경계를 설계한다
Organization은 조직의 관리 루트, Folder는 부서·환경을 묶는 단위, Project는 API·리소스·권한·결제 연결을 다루는 핵심 경계다. VM이나 버킷은 프로젝트 아래에서 관리된다. 프로젝트 이름, 프로젝트 ID, 프로젝트 번호는 다르다. CLI에는 보통 프로젝트 ID를 사용한다.

### IAM과 조직 정책
상위 계층에서 부여한 IAM allow 권한은 하위로 상속된다. 하위 프로젝트에서 같은 역할 바인딩을 지워도 상위의 부여가 사라지지 않는다. deny 정책이나 다른 제한도 있으므로 allow만 보고 최종 접근을 단정하지 않는다. Organization Policy는 생성 가능한 위치 등 리소스 구성 제약을 적용하며 IAM의 역할 부여와 목적이 다르다.

Cloud Identity/Workspace로 조직과 사용자·그룹을 관리할 수 있다. 최신 가이드의 standalone organization 경로도 구분한다. 개인 학습에 조직·도메인 구매는 필수가 아니다. 그룹에 역할을 부여하면 입퇴사 시 개인별 바인딩을 반복 수정할 필요가 줄어든다.

## 3. 실습과 관찰

프로젝트 선택기에서 프로젝트 ID와 번호를 기록한다. `gcloud projects list`와 `gcloud projects describe "$PROJECT_ID"`로 비교한다(변수 설정은 시작 가이드 참조). 조직 접근 권한이 없다면 dev/prod 폴더·프로젝트 구조를 종이에 설계한다. 실습용 조직을 새로 만들지 않는다.

## 4. 실전 시험형 예제

학습용 자체 제작 문제다. 실제 출제 문항이나 시험 덤프가 아니다.

### 문제 1 — 단일 선택

조직 공통 정책을 유지하면서 dev/prod 권한을 분리하려 한다.

A. 환경마다 공개 버킷을 쓴다
B. 환경별 프로젝트를 만들고 공통 정책을 상위에 둔다
C. 각 개발자에게 조직 Owner를 준다
D. 한 프로젝트에서 이름만 다르게 한다

### 문제 2 — 단일 선택

프로젝트에서 Viewer 바인딩을 지웠는데 직원이 계속 읽을 수 있다.

A. 폴더·조직에서 상속된 부여와 그룹 소속을 확인한다
B. VM을 재시작한다
C. 디스크를 확장한다
D. DNS TTL을 낮춘다

### 문제 3 — 단일 선택

승인된 국가의 리전에서만 자원을 만들게 해야 한다.

A. 모든 직원에게 Editor를 준다
B. 로그를 삭제한다
C. 프로젝트 표시 이름을 바꾼다
D. 지원되는 위치 제약을 Organization Policy로 적용한다

<details>
<summary>개념 확인 정답과 시험형 문제 해설</summary>

### 개념 확인

1. 아니다.

2. 없다.

3. 구성 제약과 주체의 작업 권한이다.

### 시험형 예제

**1. B** — 프로젝트는 환경별 권한·운영 경계를 제공한다. 이름만으로는 격리되지 않고 광범위 권한이나 공개화는 요구를 충족하지 않는다.

**2. A** — 상속·그룹 권한이 남을 수 있다. VM·DNS·디스크 변경으로 IAM 부여는 제거되지 않는다.

**3. D** — 위치 제약은 구성 정책 영역이다. Editor·이름·로그 삭제는 위치를 제한하지 않는다.

## 1. 개념

### 트랜잭션과 분석을 구분한다
주문·결제처럼 현재 상태를 일관되게 갱신하는 OLTP와 대량 과거 데이터를 집계하는 OLAP는 요구가 다르다. Cloud SQL은 MySQL·PostgreSQL·SQL Server 관리형 DB다. AlloyDB는 PostgreSQL 호환 워크로드를 위한 선택지이고 Spanner는 수평 확장과 강한 일관성을 요구하는 관계형 워크로드에 적합하다. 단순히 데이터가 많다는 이유만으로 Spanner를 선택하지 않는다.

Cloud SQL HA는 리전 내 존 장애에 대응하는 가용성 기능이다. Read replica는 읽기 부하 분산 등에 쓰이며 HA standby와 같지 않다. 리전 장애는 별도의 복구 설계가 필요하다. 백업과 PITR은 실수·손상에서 과거 시점으로 복구하는 용도다.

접속 문제는 DB 네트워크 경로, 인증, DB 내부 권한을 분리해 본다. Database Center는 여러 DB의 상태·문제를 통합적으로 보는 도구다. 데이터베이스 생성 후 초기 데이터 입력뿐 아니라 백업·복원·연결 수 제한을 연습해야 한다.

## 3. 실습과 관찰

기본은 비용 없는 설계 실습이다. 주문 DB의 RPO·RTO를 정하고 HA/replica/backup 역할을 적는다. 선택: 임시 Cloud SQL 인스턴스를 만들고 테이블 생성→테스트 행 입력→SELECT→백업→새 인스턴스 복원을 수행한다. 인스턴스·복원본·백업·예약 IP 등 잔존 자원을 확인한다. 회사 DB에 실행하지 않는다.

## 4. 실전 시험형 예제

학습용 자체 제작 문제다. 실제 출제 문항이나 시험 덤프가 아니다.

### 문제 1 — 단일 선택

기존 MySQL 앱을 변경을 줄여 관리형 DB로 옮긴다.

A. Cloud SQL for MySQL을 검토한다
B. BigQuery를 모든 OLTP의 교체품으로 쓴다
C. Cloud Storage 객체에 SQL 트랜잭션을 직접 실행한다
D. Cloud DNS를 DB로 쓴다

### 문제 2 — 단일 선택

한 존 장애 시 Cloud SQL의 자동 장애 조치를 원한다.

A. 백업만 수동으로 만든다
B. 지원되는 HA 구성을 사용한다
C. 공개 IP를 두 개 기록한다
D. DB 이름을 변경한다

### 문제 3 — 단일 선택

직원이 오전 데이터를 잘못 삭제했다. 장애 전 시점으로 복구해야 한다.

A. 설정된 백업과 PITR 가능 범위를 확인해 복원한다
B. DB 계정을 Owner로 만든다
C. CPU만 높인다
D. read replica가 모든 과거 시점을 갖는다고 가정한다

<details>
<summary>개념 확인 정답과 시험형 문제 해설</summary>

### 개념 확인

1. 백업/PITR 같은 별도 복구 수단이 필요하다.

2. 목적·동작이 다르다.

3. Spanner다.

### 시험형 예제

**1. A** — 기존 엔진 호환과 운영 부담을 고려하면 Cloud SQL이 맞다. 분석·객체·DNS는 해당 MySQL 실행 환경이 아니다.

**2. B** — HA는 존 장애 가용성을 위한 기능이다. 수동 백업은 복구 자료일 뿐 자동 failover가 아니다.

**3. A** — 논리적 삭제는 replica에도 전파될 수 있다. PITR·백업을 이용하며 CPU나 IAM 확대는 과거 데이터를 돌리지 못한다.

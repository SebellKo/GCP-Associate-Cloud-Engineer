## 1. 개념

### 비밀과 암호화 키의 목적
Secret Manager는 API key·비밀번호 같은 비밀의 버전과 접근을 관리한다. Cloud KMS는 암호화 키를 관리한다. CMEK는 지원 서비스의 암호화에 사용자가 관리하는 KMS 키를 사용하는 방식이다. 비밀을 담은 문자열을 저장하는 것과 데이터 암호화 키를 관리하는 것을 구분한다.

Google Cloud 기본 암호화가 있어도 조직 요구에 따라 CMEK를 선택할 수 있다. 키 위치·서비스 지원·service agent 권한을 맞춰야 한다. 키를 비활성화·파기하면 데이터 접근과 복구에 영향을 줄 수 있다. 암호화는 IAM 접근 통제나 백업을 대체하지 않는다.

보안 운영은 비밀 회전→앱 반영→이전 버전 중지·검증 순서로 계획한다. 비밀 값은 로그·명령 기록·이미지·Terraform state에 남지 않도록 한다. 감사 로그에서 접근 주체를 확인하되 비밀 본문을 수집해 감사를 하려 하지 않는다. private network와 데이터 권한도 따로 검증한다.

## 3. 실습과 관찰

기본은 설계: 앱 API key 전달과 bucket CMEK의 identity·권한을 구분한다. 선택: 무가치한 테스트 문자열만 Secret Manager에 넣고 새 버전을 만든 뒤 이전 버전을 중지한다. 테스트 secret·버전과 연결 자원을 정리한다. KMS 키 버전 파기는 복구 제약이 있으므로 이 교재에서는 실행하지 않는다.

## 4. 실전 시험형 예제

학습용 자체 제작 문제다. 실제 출제 문항이나 시험 덤프가 아니다.

### 문제 1 — 단일 선택

앱에서 사용할 결제 API key를 안전하게 버전 관리한다.

A. DNS A 레코드에 넣는다
B. Secret Manager에 저장하고 runtime identity에 접근 권한을 준다
C. public README에 쓴다
D. Dockerfile에 평문으로 넣는다

### 문제 2 — 단일 선택

CMEK bucket 접근이 키 권한 오류로 실패한다.

A. 버킷을 무조건 공개한다
B. 서비스가 사용하는 identity의 KMS 권한·키 상태·위치를 확인한다
C. VM CPU를 늘린다
D. 모든 로그를 지운다

### 문제 3 — 단일 선택

보안팀이 키를 즉시 파기하자고 한다. 운영 담당자의 우선 검토는?

A. 백업도 전부 삭제한다
B. 암호화된 데이터의 접근·복구 의존성과 요구사항을 확인한다
C. 비밀을 공개한다
D. 아무 영향이 없다고 단정한다

<details>
<summary>개념 확인 정답과 시험형 문제 해설</summary>

### 개념 확인

1. 비밀 값 관리와 암호화 키 관리다.

2. 아니다.

3. 의존 서비스·데이터 접근·복구 영향이다.

### 시험형 예제

**1. B** — 비밀의 버전·권한 관리를 사용한다. 이미지·README·DNS 노출은 비밀 관리가 아니다.

**2. B** — 암호화 경로의 키 권한과 상태를 진단한다. 공개화·CPU·로그 삭제는 복호화 권한을 해결하지 않는다.

**3. B** — 키 수명 주기는 데이터 가용성에 영향을 준다. 무영향 가정과 데이터·비밀 파괴는 잘못이다.

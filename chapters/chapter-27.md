# Chapter 27. 통합 프로젝트: 배포부터 운영·정리까지

공식 가이드 연결: **1 / 2 / 3 / 4** · 권장 2~3시간(통합 실습은 4~6시간)

## 1. 개념

### 목표와 아키텍처
작은 Go HTTP API를 Cloud Build→Artifact Registry→Cloud Run으로 배포한다. 전용 runtime service account를 연결하고 Cloud Storage의 테스트 객체를 읽을 수 있는 최소 권한을 구성한다. 시작은 DB 없이 상태 없는 서버를 운영해 배포·인증·로그·복구의 연결을 익힌다. DB 확장은 Chapter 11의 설계로 진행한다.

운영 절차는 배포 전 프로젝트·계정 확인, 새 버전 검증, 로그·지표 관찰, 필요 시 이전 revision으로 복구, 자원 정리 순서다. IAM 문제와 앱 문제를 의도적으로 섞지 않고 한 변수씩 바꿔 결과를 기록한다. 아래 프로젝트의 bucket 권한은 IAM 구성 확인용이며 샘플 서버가 Storage SDK를 호출하는 기능까지 구현한 것은 아니다. 그 확장은 선택 과제다.

완료 증거는 호출 결과, revision/digest, IAM 범위, 오류 로그 검색 조건, rollback 절차, 삭제 목록이다. 배포 URL만 있으면 운영을 마친 것이 아니다. 실습 기록에는 계정 token이나 비밀을 넣지 않는다.

## 3. 실습과 관찰

[통합 실습 전체 절차](../labs/capstone.md)를 따른다. 준비→빌드→비공개 호출→운영 점검→정리의 각 단계 증거를 남긴다. GCP 배포는 본인의 결제·실습 권한을 확인한 뒤 실행한다. 오류 상황에서는 전체 권한 확대보다 정확한 단계 identity를 조사한다.

## 4. 실전 시험형 예제

학습용 자체 제작 문제다. 실제 출제 문항이나 시험 덤프가 아니다.

### 문제 1 — 단일 선택

새 API가 배포됐지만 private endpoint를 익명 호출하면 실패한다.

A. 인증된 호출과 Invoker 권한을 확인한다
B. 무조건 전 세계에 공개한다
C. DB를 지운다
D. KMS 키를 파기한다

### 문제 2 — 단일 선택

교재 실습 종료 후 Cloud Run만 지웠다. 더 확인할 자원은?

A. DNS 표기법만
B. 브라우저 확대 배율만
C. Artifact Registry 이미지·bucket·계정과 빌드 관련 저장 자원
D. 로컬 편집기 테마만

### 문제 3 — 단일 선택

빌드 성공 후 서비스가 bucket에서 403을 받는다.

A. 버킷을 공개한다
B. 모든 계정을 Owner로 만든다
C. 빌드 성공이므로 Google 장애라고 단정한다
D. runtime identity의 bucket 권한과 실제 대상 경로를 점검한다

<details>
<summary>개념 확인 정답과 시험형 문제 해설</summary>

### 개념 확인

1. 빌드·배포·실행 주체다.

2. 버전·로그·권한·복구·삭제 기록이다.

3. SDK 호출 구현이 별도로 필요하다.

### 시험형 예제

**1. A** — 비공개 서비스는 인증·인가를 검증한다. 공개화·삭제·파기는 기본 해결책이 아니다.

**2. C** — 배포 연관 자원이 남아 과금·권한을 유지할 수 있다. 나머지는 클라우드 자원 정리와 무관하다.

**3. D** — 실행 주체는 빌드 주체와 다르다. 정확한 권한·대상 검증이 필요하다.
